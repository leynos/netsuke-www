    CLI & Config
    CLI reference

    Command Line & Configuration

    Master the Netsuke CLI to build targets, inspect manifests, and control output. Configuration layers belong to the CLI, the environment, and config files rather than hidden defaults.

    CLI Commands

    build

    Primary

    Builds the specified targets and their dependencies. This is the main entry point for day-to-day usage.

    --jobs, -j Number of parallel jobs (default: auto)
    --verbose, -v Show full command lines
    --file, -f Read a manifest from a custom path
    netsuke build app

    query

    Analysis

    Graph and manifest inspection commands help explain what Netsuke is about to hand to Ninja.

    manifest Render or inspect the manifest without building
    graph Visualize the dependency graph
    netsuke manifest --file Netsukefile

    clean

    Maintenance

    Removes output files and caches. Use --expunge to remove the entire output directory.

    netsuke clean --expunge
    user@dev:~/netsuke-project
    ➜ netsuke build app --verbose
    INFO: Parsed Netsukefile and expanded 3 targets
    INFO: Wrote build.ninja

    app -> main.o

    ➜ _

    Pro Tip: Watch Mode

    Use netsuke build ... --watch to automatically rebuild targets when source files change. Perfect for rapid development loops.

    Configuration

    The CLI design document describes layered configuration: command-line flags, environment variables, and config files. Use configuration to choose manifest paths, jobs, locale, and output style rather than to hide core build logic.

    Config Keys

    • [build]
    • [ui]
    • [locale] 
    [build]
# Fail the build on the first error
keep_going = false
# Number of parallel jobs (0 = auto)
jobs = 0
# Optional manifest path override
file = "Netsukefile"

[ui]
# Reduce animated progress output
quiet = false
# Disable colour in plain terminals
color = "auto"

[locale]
# Preferred locale for messages
language = "en-GB"
# Fall back to built-in English resources
fallback = "en-US"

    Security Model

    Safe by Default

    The reviewed docs emphasize safer command construction, clear diagnostics, and explicit manifest structure. This page therefore sticks to the validation boundaries Netsuke actually documents.

    YAML first

    The manifest must be valid YAML before any template expansion happens. Structural mistakes fail early, before commands are generated.

    Shell escaping

    Interpolated values in commands and scripts are escaped by default, with explicit opt-outs for raw usage where the author really means it.

    Typed diagnostics

    CLI errors are designed to carry context, hints, and localized output rather than dropping raw parser failures on the floor.

    Troubleshooting

    Common Issues

    • Rule mismatch: A target defined more than one of rule, command, or script. Keep the recipe singular.
    • Template failure: A variable or macro expanded unexpectedly. Check the rendered string fields and the vars precedence.
